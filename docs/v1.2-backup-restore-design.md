# InkFlow V1.2 完整备份与灾难恢复 · 第一阶段分析报告与技术设计

> 版本：草案 v1（待确认）
> 分析基准：`main` @ `1a13c1c`（工作区干净），Node v24.19.0
> 范围：只做分析、设计与分批计划；本文确认前不进入 Batch 1 实现。

## 0. 结论摘要（先看这里）

1. **当前没有真正的服务端备份能力。** 管理台里的“导出 JSON 备份 / 恢复 JSON 备份”只读写浏览器
   `localStorage` 缓存（`src/services/storage.ts:1393`、`AdminDashboard.tsx:724`），不包含 SQLite、
   历史版本文件、服务端附件和用户身份，不能用于灾难恢复。`storage/backups/` 目录虽然存在，但没有任何代码使用。
2. **不能“复制 storage 目录”做备份。** 数据库处于 WAL 模式，已提交事务可能只存在于 `-wal` 文件中；
   直接复制 `knowledge_hub.sqlite` 会得到旧快照，复制 `.sqlite + -wal + -shm` 又在并发写时无法保证三者同代。
   必须使用 SQLite 在线备份 API（`node:sqlite` 已提供 `backup()`）生成一致快照。
3. **现有并发控制只覆盖“文档保存/删除 + 标签清理 + 历史清理”，没有覆盖附件、启动重建和备份本身。**
   附件上传、附件清理、`listAssets()` 的磁盘对账、`ensureInitialPhysicalDocs()`、
   `rebuildAssetReferences()` 都是裸写，足以在备份时制造“数据库与文件不同代”。
4. **推荐的一致性核心：一个全局共享/独占租约 `ConsistencyGate`。**
   - 所有会改动 `documents/`、`revisions/`、`assets/` 或与之相关 DB 行的操作持有 **共享租约**；
   - 备份/恢复持有 **独占租约**；
   - 备份在独占租约内完成 “DB 在线快照 + 文件硬链接快照（manifest）”，**随后立即释放租约**，
     压缩、哈希、下载都在硬链接快照上进行。这样写入停顿只等于“目录遍历 + 硬链接”，而不是“压缩整个知识库”。
5. **恢复采用“暂存目录 + 全量校验 + 原子换入 + 失败回滚”**，并在整个恢复期间进入持久化维护状态；
   恢复前自动生成一份 `pre-restore` 备份。任何失败都必须回到恢复前的数据，绝不能留下半套数据。
6. **备份包格式：单个 ZIP**，内含 `manifest.json` + `database/knowledge_hub.sqlite` +
   `documents/` + `revisions/` + `assets/`。所有路径使用 POSIX `/`；排除 `.bak`、`.save.pending`、
   `.delete.pending`、`*.tmp`、`backups/`、`.env`、日志和 `sessions` 表。
7. **现有 V1.1 机制全部保留**：`.bak` / `.save.pending` / `.delete.pending` / `document_hash`
   仍是保存与删除的崩溃恢复机制；备份只是在其之上增加“全库一致快照”，不替换它们。

## 1. 当前项目真实的数据存储结构

### 1.1 目录布局

```
<storage root = INKFLOW_DATA_DIR 或 <cwd>/storage>
├── documents/{documentId}/index.md          # Markdown SSOT（frontmatter + 正文）
│   └── 同目录可能出现：index.md.bak、.save.pending、.delete.pending、index.md.<ts>.<rand>.tmp
├── revisions/{documentId}/{revisionId}.md   # 每次保存生成的历史快照
├── assets/{assetId}.{ext}                   # 附件物理文件
├── database/knowledge_hub.sqlite            # 可通过 INKFLOW_DB_PATH 指向任意路径
│   ├── ...-wal / ...-shm                    # WAL 模式
├── backups/                                 # 空目录，当前无代码使用
└── .gitkeep
```

- 根目录解析：`server/db/sqlite.ts:7`、`server/services/fileStorageService.ts:6`。
- 数据库路径可被 `INKFLOW_DB_PATH` 覆盖到数据目录之外（`server/db/sqlite.ts:11`）。
  **备份/恢复必须同时处理“DB 不在 dataDir 内”的部署。**

### 1.2 SQLite 表（`server/db/schema.ts`）

| 表 | 作用 | 与文件系统的关系 |
| --- | --- | --- |
| `users` | 主理人/用户身份，scrypt 密码哈希 | 无 |
| `sessions` | 登录会话（token SHA-256） | 无；**备份时必须剔除** |
| `categories` | 分类字典 | 无直接文件；文档有 `category_name` |
| `tags` | 标签字典 | 无；与 Markdown frontmatter 的 `tags` 双向对应 |
| `documents` | 文档元数据、可见性、版本号、`content_hash`、`document_hash`、`file_path` | `documents/{id}/index.md` |
| `document_tags` | 文档↔标签 | 派生自文档 |
| `document_revisions` | 历史版本元数据、`snapshot_path` | `revisions/{docId}/{revId}.md` |
| `shares` | 分享 token（哈希）、密码哈希、过期/次数 | 无 |
| `assets` | 附件元数据、`storage_path`、`checksum` | `assets/{assetId}.{ext}` |
| `document_assets` | 文档↔附件引用（由 Markdown AST 解析生成） | 派生自文档 |
| `documents_fts` | FTS5 全文索引（内部内容表） | 派生自文档 |
| `recovery_codes` | 一次性恢复码（哈希） | 无 |
| `system_settings` | `owner_initialized` 等单向标记 | 无 |

关键字段与语义：

- `documents.file_path`：**相对 storage root 的路径**，由 `path.relative()` 生成，Windows 下可能是 `documents\id\index.md`。
- `document_revisions.snapshot_path`：同上，Windows 分隔符会写入数据库。
- `assets.storage_path`：同上；读取时经 `resolveWithinStorage()` 做路径包含校验（`fileStorageService.ts:62`）。
- `documents.content_hash`：**仅正文**的 SHA-256 前 16 位（`documentService.ts:191`）。
- `documents.document_hash`：**frontmatter + 正文**全文件 SHA-256，是保存崩溃恢复的提交标记（`documentService.ts:203`）。
  旧数据可能为 `NULL`，由 `backfillDocumentHashes()` 补齐（`documentService.ts:787`）。
- `documents.version_count` 是乐观锁版本号；`document_hash` 与 `content_hash` 都不对访客暴露。

### 1.3 Markdown frontmatter

`buildFrontmatterBlock()` 写入：`id/title/slug/category/tags/visibility/status/author/pinned/content_hash/created_at/updated_at`
（`documentService.ts:158`）。注意：frontmatter 中的 `content_hash` 是正文哈希，不是全文件哈希。

### 1.4 派生数据与事实来源

- Markdown 是内容 SSOT；SQLite 是索引/元数据/权限/身份。
- `document_assets`、`documents_fts` 完全可由 Markdown 重建。
- `document_revisions` 的**文件**是历史内容；DB 行是索引。
- **用户、密码哈希、分享、分类、标签字典、恢复码只存在于 SQLite**，Markdown 目录无法重建它们。
  这是“只备份 Markdown 不够”的根本原因。

## 2. 所有数据写入路径及其并发控制机制

### 2.1 现有锁

| 机制 | 位置 | 语义 |
| --- | --- | --- |
| `AsyncReadWriteLock`（`maintenanceLock`） | `documentService.ts:213` | 文档写/删/单文档历史清理持 **read**；标签清理、全局历史清理持 **write**（写优先） |

| --- | --- | --- | --- | --- | --- |

### 2.3 现有事务实现的一个真实风险

`saveDocumentLocked()` 在 `BEGIN IMMEDIATE`（`documentService.ts:917`）之后，
`await fileStorage.saveRevisionSnapshot(...)`（`documentService.ts:995`）才写文件。
Node 单线程意味着这个 `await` 会让出事件循环；**其他请求的 DB 写入会落在同一个连接、同一个事务里**。
后果：

- 另一个请求的 `BEGIN IMMEDIATE`（初始化/重置密码/标签清理）会因“事务中不能再开事务”失败，
  其 `catch` 执行 `ROLLBACK`，把正在进行的文档保存事务一起回滚；
- 另一个请求的普通 INSERT/UPDATE 会被算进文档保存事务，保存失败回滚时被无辜回滚。

这不常触发，但它会直接破坏备份时的“DB 快照内部一致”前提。**Batch 1 必须消除所有跨 `await` 的事务。**

### 2.4 现有删除/清理顺序的悬空引用

- #4/#5/#6 历史清理：先 `fs.rm(revision.md)`，后 `DELETE FROM document_revisions`。
  若进程在两步之间退出，DB 行仍指向不存在的快照 → 恢复演练和完整性校验会报“文件缺失”。
- #8/#9 附件删除：先 `unlink`，后删 DB 行；同理。
- 正确顺序应是“先删 DB 行（可重试的幂等状态），后删文件”，崩溃最多留下孤儿文件（无害，可再次清理）。

## 3. 当前备份与恢复相关能力

| 能力 | 现状 | 评价 |
| --- | --- | --- |
| 文档保存崩溃恢复 | `.bak` + `.save.pending` + `document_hash` | V1.1 已实现，有效 |
| 文档删除崩溃恢复 | `.delete.pending` + DB 行判定 | V1.1 已实现，有效 |
| 从磁盘重建索引 | `rebuildIndexFromDisk()` | 只能恢复 Markdown 正文与 frontmatter 派生的信息；**丢失用户/会话/分享/历史版本行/附件 DB 行/分类描述/恢复版本序号**，且会为每篇文档新增 revision |
| 附件对账 | `listAssets()` 扫描目录补 DB 行 | 仅补元数据，checksum 为空，不是恢复 |
| 附件引用重建 | `ensureAssetReferences()` | 派生表重建，不是备份 |
| 前端导出 Markdown ZIP | `exportAllAsZip()` | 基于 localStorage 缓存；附件只导出 dataUrl 内联的旧数据；不含 DB/历史/用户 |
| 前端“完整 JSON 备份” | `exportFullBackupJson()` | **只是 localStorage 快照**，与服务端 SSOT 无关，不能作为灾难恢复 |
| `storage/backups/` | 空目录 | 未使用 |
| 自动备份 / 保留策略 / 完整性校验 / 恢复 | 无 | V1.2 范围 |

> 结论：V1.1 的恢复能力是“单文档、崩溃瞬间”的，不是“全库、跨环境”的。
> `rebuild-index` 不能替代完整恢复，因为 SQLite 里有大量 Markdown 无法重建的数据。

## 4. 可能导致备份不一致的风险（按严重度）

### P0

1. **直接复制 WAL 数据库**：可能读到缺失最新事务的快照，或 `-wal/-shm` 与主库不同代，恢复后数据库损坏/回退。
2. **没有全局“DB+文件”冻结点**：备份遍历 `documents/` 时，保存/删除/附件上传可以同时发生，导致：
   - DB 快照里有文档行，ZIP 里没有 `index.md`；
   - ZIP 里有附件文件，DB 快照里没有 asset 行；
   - DB 快照里的 `document_hash` 与 ZIP 里的 `index.md` 不匹配。
3. **备份包含 `.bak` / `.save.pending` / `.delete.pending`**：这些是“未提交/待删除”状态，不是正常数据；
   恢复后可能复活已删除文档，或让新环境一启动就进入 `SAVE_RECOVERY_REQUIRED`。
4. **事务跨 `await`**（2.3）：备份期间若发生跨请求事务污染，DB 快照可能包含被回滚的逻辑状态。
5. **恢复没有原子换入**：先删旧数据再拷贝新数据，中途失败会同时失去新旧两份。

### P1

6. 附件上传/清理竞争：清理可能删掉尚未 INSERT 的上传文件；删除附件先删文件导致 DB 行悬空。
7. 历史清理先删文件导致 DB 行悬空。
8. `listAssets()` 在 GET 中写库，使只读请求改变备份状态。
9. 启动后异步 `ensureAssetReferences()` 与在线请求交错。
10. `ensureInitialPhysicalDocs()` / `rebuildIndexFromDisk()` 的多次保存不是一个原子集合，备份可能抓到“重建到一半”的状态。
11. **跨平台路径**：`file_path`/`snapshot_path`/`storage_path` 可能含 Windows `\`，在 Linux 上恢复后 `resolveWithinStorage()` 无法解析附件路径。
12. **无 schema 版本号**：无法判断备份是哪个结构版本，也无法安全地做前向迁移。
13. **备份包含 `sessions`**：会话 token 哈希随包扩散；恢复到新环境后旧会话仍然有效（若未清空）。
14. 数据库可能在 `INKFLOW_DATA_DIR` 之外（`INKFLOW_DB_PATH`），只打包 `storage/` 会漏掉 DB。

### P2

15. 单实例只检查 `cluster.isWorker`，两个独立进程仍可同时写同一 storage。
16. 备份 ZIP 在内存中生成/解压（JSZip）会受大附件影响；磁盘空间不足时可能留下半个包。
17. 符号链接：备份遍历若跟随 symlink，可能把 storage 外文件打包；恢复若接受 symlink 条目，可能写出目录。
18. 浏览器 `localStorage` 中的评论/论坛数据不在服务端，完整备份无法覆盖。
19. `documents_fts` 是派生表，恢复后若未重建，可能与正文不一致。

## 5. V1.2 完整技术设计

### 5.1 组件图

```
HTTP / CLI
   │
   ├── BackupController (routes)
   │      ├── BackupService      —— 创建/校验/列出/删除/下载
   │      ├── RestoreService     —— 暂存/校验/换入/回滚/报告
   │      └── BackupScheduler    —— 定时/保留/限容/失败日志
   │
   ├── ConsistencyGate (shared/exclusive lease)
   │      ├── documentService (save/delete/revision cleanup)
   │      ├── assetService (upload/delete/cleanup/reconcile)
   │      ├── seedData (seed/rebuild)
   │      ├── BackupService (exclusive)
   │      └── RestoreService (exclusive + maintenance)
   │
   ├── MaintenanceState (persisted .restore-state.json / .maintenance.json)
   ├── SnapshotStore (hardlink/copy staging)
   ├── ArchiveCodec (JSZip; path/entry limits)
   └── IntegrityVerifier (hash / sqlite integrity / cross-reference)
```

**复用而非新增依赖**：ZIP 继续用已有的 `jszip`；数据库快照用 `node:sqlite` 的 `backup()`（本机已实测可用）；
不引入 `archiver`、`yauzl`、`better-sqlite3` 等新依赖。

### 5.2 ConsistencyGate

把 `documentService` 内的 `AsyncReadWriteLock` 提取为独立单例，并改为**严格 FIFO**
（读者在队首时成批授予；写者到达队首后等待当前读者排空并单独运行），
从而同时避免“写者被连续保存饿死”和“读者被连续独占任务饿死”。
并增加“代计数”和“维护状态”：

```ts
// server/services/consistencyGate.ts
export class ConsistencyGate {
  acquireShared(): Promise<Release>;   // 文件系统写操作
  acquireExclusive(): Promise<Release>; // 备份/恢复/全库重建
  get generation(): number;            // 每次独占/共享写完成 +1，用于断言
  isExclusiveHeld(): boolean;
}
export const consistencyGate = new ConsistencyGate();
```

规则：

| 操作 | 租约 |
| --- | --- |
| `saveDocument`、`deleteDocument`、单文档历史清理、单版本删除 | shared |
| 附件上传/删除/孤儿清理、`listAssets` 对账 | **shared（新增）** |
| 全局历史清理、标签字典清理 | exclusive（沿用） |
| `ensureInitialPhysicalDocs`、`rebuildIndexFromDisk`、`rebuildAssetReferences` | **exclusive（新增）** |
| 创建备份、恢复 | exclusive |
| 纯 DB（分类、分享、认证、会话） | 不取租约；由 HTTP 维护中间件在恢复期间统一 503 |

注意：现有 `withSaveGate()` 继续存在，内部改为调用 `consistencyGate.acquireShared()`，
这样 `runExclusiveMaintenance()` 的既有语义和测试不变。

### 5.3 备份算法（核心）

```ts
async function createBackup(kind: 'manual'|'scheduled'|'pre-restore'): Promise<BackupResult> {
  const release = await consistencyGate.acquireExclusive();
  const staging = path.join(dataDir, 'backups', '.staging', backupId);
  try {
    // 1. 先把现场恢复到可备份状态（不跳过任何 V1.1 机制）
    await documentService.recoverPendingDeletions();
    await documentService.recoverPendingSaves();
    const pending = await snapshotStore.findPendingArtifacts(); // .bak/.save.pending/.delete.pending/*.tmp
    if (pending.length) throw new BackupBlockedError(pending);  // 拒绝产生“半提交”备份

    // 2. 结构校验：DB ↔ 磁盘必须已经一致
    await integrityVerifier.assertFileStateMatchesDb();

    // 3. SQLite 在线备份（WAL 安全；此时无任何文档/附件写事务）
    await fs.mkdir(path.join(staging, 'database'), { recursive: true });
    await sqliteBackup(getDatabase(), path.join(staging, 'database', 'knowledge_hub.sqlite'));

    // 4. 剔除会话：备份包不应携带可用的登录会话
    scrubSnapshotSessions(path.join(staging, 'database', 'knowledge_hub.sqlite'));
    await checkpointAndCloseSnapshot(...);

    // 5. 文件快照：优先硬链接，失败回退复制（仍在本租约内，保证同代）
    const files = await snapshotStore.capture(staging, {
      documents: 'documents',
      revisions: 'revisions',
      assets: 'assets',
      exclude: ['.bak', '.save.pending', '.delete.pending', '*.tmp', '.gitkeep'],
    });

    // 6. 写入 manifest 骨架（文件哈希稍后在租约外计算）
    await writeManifest(staging, { kind, files, dbPath, schemaVersion, appVersion });

    // 7. 释放写租约：后续哈希/压缩只读硬链接快照，不再阻塞业务
  } finally {
    release();
  }

  // 8. 租约外：逐个文件计算 SHA-256，与 DB 的 document_hash/checksum 交叉校验
  const manifest = await hashSnapshotAndValidate(staging);
  // 9. 压缩为 ZIP（.part → fsync → rename），计算整包 SHA-256
  await archiveCodec.pack(staging, zipPath);
  // 10. 落库 backup_jobs + 保留策略 + 清理 staging
  await finalizeBackup(...);
}
```

#### 为什么这个顺序能保证一致

- **独占租约先于 DB 快照**：所有会改变 `documents/revisions/assets` 及其 DB 行的操作都被挡住，
  因此 DB 快照与随后捕获的文件属于同一逻辑代。
- **硬链接快照后释放租约**：业务恢复写入。由于项目内所有正常写文件都是
  “临时文件 + `rename`” 或 “`wx` 新建”，**已存在的 inode 不会被原地修改**；
  硬链接在快照目录里继续指向旧 inode，后续保存/删除不会改变快照内容。
- **`.bak`/`.pending` 先恢复再排除**：要么现场已被修复成一致状态，要么备份直接失败并列出待处理文档，
  绝不把临时文件当成正常数据。
- **DB 快照内部的 WAL 一致性**：由 SQLite Online Backup API 保证（已实测：30 万行库在并发读写下
  2.3s 完成，结果无错误、为某一提交点的内部一致快照）。备份期间不应该有文档/附件写事务；
  会话 `last_seen` 之类的纯 DB 写即使穿插，也不会造成 DB 内部撕裂。

#### 运行环境与回退

- 本机 Node v24.19.0 已实测 `node:sqlite` 提供模块级 `backup(sourceDb, path)`，返回 Promise；
  30 万行、含 WAL 的库在并发读写压力下 2.3s 完成且无错误。
- 启动时做能力探测：`typeof sqlite.backup === 'function'`。
  - 可用 → 使用 Online Backup API；
  - 不可用 → 在同一独占租约内使用 `VACUUM INTO '<staging>/database/...sqlite'`
    （同步、会阻塞事件循环，但语义一致；文档需注明该回退会延长写停顿）。
- 快照生成后立即在其上执行 `DELETE FROM sessions`，再
  `PRAGMA journal_mode=DELETE` + `PRAGMA wal_checkpoint(TRUNCATE)` 并关闭；
  实测关闭后目录中只保留单个 `.sqlite` 文件，不会把 `-wal/-shm` 打进包。
- `db.serialize()` 也能得到一致快照，但会把整库读入内存，不作为主方案。

#### 硬链接不可用时

`fs.link` 在跨卷/不支持的文件系统会失败（`EXDEV`/`EPERM`/`ENOTSUP`）。此时在**仍持有独占租约**的情况下
逐文件复制到 staging。这会把写停顿延长为“复制全部文件”，但语义仍然正确。staging 固定放在
`<dataDir>/backups/.staging/`（与 `documents/revisions/assets` 同卷），以最大化硬链接成功率。

### 5.4 恢复算法（核心）

```ts
async function restore(packagePath: string, options: RestoreOptions) {
  await maintenance.enter('restore', restoreId);   // 持久化 .restore-state.json
  const release = await consistencyGate.acquireExclusive();
  try {
    // 1. 归档校验（未解压前）：条目数/总大小/路径穿越/symlink/允许的根目录
    const entries = await archiveCodec.inspect(packagePath);

    // 2. 解压到 <dataDir>/.restore/<restoreId>/（同卷）
    const staged = await archiveCodec.extract(packagePath, stagingDir, entries);

    // 3. 全量校验：manifest 哈希、SQLite integrity_check、foreign_key_check、
    //    DB 行 ↔ 文件、附件 checksum、文档 document_hash、路径包含
    const report = await integrityVerifier.verifyPackage(staged, manifest);

    // 4. 恢复前保护：对当前环境生成 pre-restore 备份（目标为空时可跳过）
    const safety = await backupService.createPreRestoreBackup();

    // 5. 规范化跨平台路径 + 清空 sessions + 重建 FTS（在 staging DB 上完成）
    await normalizeStagedDatabase(staged);

    // 6. 关闭当前数据库连接
    closeDatabase();

    // 7. 原子换入：
    //    current documents/revisions/assets -> backups/rollback-<id>/
    //    staged   documents/revisions/assets -> 正式位置
    //    DB：staged snapshot -> getDbPath()（临时文件 + rename）
    await swapDirectories(staged, rollbackDir, dbTarget);

    // 8. 重新打开数据库（触发 schema 迁移）、重建 FTS、后置校验
    getDatabase();
    await rebuildFtsFromMarkdown();
    await integrityVerifier.verifyLiveState();

    // 9. 成功：写恢复报告，清除维护状态
    await maintenance.complete(report);
  } catch (err) {
    // 10. 失败回滚：换回 rollbackDir 与旧 DB，重新打开并校验
    await rollbackSwap();
    await maintenance.fail(err);
    throw err;
  } finally {
    release();
  }
}
```

#### 恢复状态机（持久化）

`<dataDir>/.restore-state.json`：

```json
{
  "restoreId": "rst_...",
  "phase": "staging|validated|safety-backup|swapping|swapped|verifying|completed|failed|rolled-back",
  "stagingDir": ".restore/rst_...",
  "rollbackDir": "backups/rollback-rst_...",
  "dbTarget": "/abs/path/knowledge_hub.sqlite",
  "dbBackupPath": "backups/rollback-rst_.../knowledge_hub.sqlite",
  "startedAt": "...",
  "pid": 1234,
  "reportPath": "backups/restore-reports/rst_....json"
}
```

启动顺序（`server.ts`）必须变成：

1. 读取并恢复中断的恢复任务（`restoreCoordinator.recoverInterruptedRestore()`）；
2. 若维护状态仍未清除 → **不进入正常业务**，只提供健康检查/维护接口；
3. 执行 V1.1 的删除/保存恢复；
4. `ensureInitialPhysicalDocs()`（独占租约）；
5. `ensureAssetReferences()`（独占租约，或移到 listen 前）；
6. `listen()`；
7. 启动自动备份调度器。

#### 换入的跨平台细节

- 换入的是 `documents/`、`revisions/`、`assets/` 三个子目录和 DB 文件，**不整体 rename `storage/`**
  （因为 `backups/`、`database/` 路径可能被外部配置，且整体 rename 会让当前进程的路径失效）。
- Windows 上先 `closeDatabase()`，否则文件被占用无法 rename；`EPERM`/`EBUSY` 做有限重试。
- 如果 `INKFLOW_DB_PATH` 指向 dataDir 之外，DB 换入按“临时文件 + rename”处理到该路径；
  回滚时保留旧 DB 文件。

### 5.5 维护状态

- 持久化文件：`<dataDir>/.maintenance.json`（`{active, reason, restoreId, startedAt, pid}`）。
- HTTP 中间件：除 `GET /api/health`、`GET /api/v1/system/maintenance`、恢复状态查询外，
  所有写请求返回 `503 MAINTENANCE_MODE`；读请求可继续（但恢复期间 DB 可能关闭，建议统一 503 并给 Retry-After）。
- 备份**不**进入维护模式（只短暂持独占租约），因此备份期间的保存请求只会排队等待，不会 503。

### 5.6 定时备份

- 进程内调度器，不新增依赖；`setTimeout` 对齐下一次执行时间，避免 `setInterval` 漂移。
- 防重复：
  - 进程内 `running` 标志；
  - 文件锁 `<backupDir>/.backup.lock`（`{pid, backupId, startedAt, heartbeatAt}`）；
  - DB 中 `backup_jobs` 状态。
- 异常退出恢复：启动时检查锁文件：
  - pid 不存在或 heartbeat 超时（默认 10 分钟）→ 将上次 running 任务标记 `aborted`，删除锁，按计划重试；
  - pid 存在且是当前进程 → 说明上次未清理，标记失败后重试。
- 保留策略：
  - 保留最近 N 份（默认 7）；
  - 可选 `RETENTION_DAYS`；
  - 总容量上限（默认 5 GiB），超限从最旧的非受保护备份开始删；
  - **永不删除**：当前正在写的、最后一份成功备份、`pre-restore` 保护期内备份。
- 失败日志：`backup_jobs.error` + `<backupDir>/backup.log`（JSON Lines，0600）。
- 估算空间：打包前计算源文件总大小，要求剩余空间 ≥ `源大小 × 1.2 + DB 大小 × 2`，不足直接失败并记录。

### 5.7 完整性验证

两个入口：

1. `verifyPackage(zipPath)`：只读备份包，验证：
   - ZIP CRC 与条目结构；
   - `manifest.json` schema、`formatVersion`；
   - 每个条目大小/SHA-256 与 manifest 一致，且无 manifest 外条目（白名单目录）；
   - SQLite `PRAGMA integrity_check`、`PRAGMA foreign_key_check`；
   - `documents` 行 ↔ `documents/{id}/index.md`、`document_hash` 匹配；
   - `document_revisions` 行 ↔ `revisions/{doc}/{rev}.md`；
   - `assets` 行 ↔ `assets/*`、文件大小与 SHA-256 匹配；
   - `document_assets` 引用的 asset 存在；
   - FTS 行数/内容可由文档重建；
   - 拒绝 `.bak/.pending/*.tmp`。
2. `verifyLiveState()`：对当前运行环境做同样交叉校验（独占租约内），用于“体检”与恢复后验收。

输出结构化报告：

```ts
interface VerificationReport {
  ok: boolean;
  checkedAt: string;
  formatVersion: number;
  schemaVersion: number;
  counts: { documents; revisions; assets; tags; categories; users; shares };
  checks: Array<{ name: string; ok: boolean; detail?: string }>;
  missingFiles: string[];
  orphanFiles: string[];
  hashMismatches: Array<{ path: string; expected: string; actual: string }>;
  sqliteIntegrity: string;
  foreignKeyViolations: number;
}
```

### 5.8 备份期间的读一致性

`listDocuments()` 会一边读 DB 一边读 `index.md`（`documentService.ts:427`）。备份不改变这一点；
普通读取可能看到“DB 已提交、文件已 rename”的同一代状态（V1.1 的提交顺序保证了这一点），
不会因为备份而变差。恢复期间读请求统一走维护中间件。

## 7. 数据备份格式设计

### 7.1 包结构

```
inkflow-20261112-030000-manual-bkp_xxx.zip
├── manifest.json
├── database/
│   └── knowledge_hub.sqlite
├── documents/
│   └── {documentId}/index.md
├── revisions/
│   └── {documentId}/{revisionId}.md
└── assets/
    └── {assetId}.{ext}
```

- 不包含：`storage/backups/`、`.gitkeep`、`.bak`、`.save.pending`、`.delete.pending`、`*.tmp`、`.env*`、日志、密钥。
- 所有条目路径必须是 **POSIX 相对路径**，且只允许上述四个根。
- ZIP 使用 deflate；单文件原样存储也可，压缩级别可配置。
- 包文件名与内部 `manifest.backupId` 同名，便于去重与保留策略。

### 7.2 `manifest.json`

```json
{
  "format": "inkflow-backup",
  "formatVersion": 1,
  "backupId": "bkp_mabc1234_...",
  "kind": "manual",
  "createdAt": "2026-11-12T03:00:00.000Z",
  "appVersion": "1.2.0",
  "schemaVersion": 2,
  "minAppVersion": "1.2.0",
  "source": {
    "platform": "linux",
    "node": "v24.19.0",
    "dataDirBasename": "storage"
  },
  "database": {
    "path": "database/knowledge_hub.sqlite",
    "size": 123456,
    "sha256": "…",
    "integrityCheck": "ok",
    "foreignKeyViolations": 0,
    "sessionsExcluded": true
  },
  "counts": {
    "documents": 42,
    "revisions": 310,
    "assets": 17,
    "tags": 25,
    "categories": 6,
    "users": 1,
    "shares": 3
  },
  "files": [
    {
      "path": "documents/doc_x/index.md",
      "kind": "document",
      "id": "doc_x",
      "size": 1024,
      "sha256": "…",
      "mtime": "2026-11-12T02:00:00.000Z"
    },
    {
      "path": "revisions/doc_x/rev_y.md",
      "kind": "revision",
      "documentId": "doc_x",
      "id": "rev_y",
      "size": 900,
      "sha256": "…"
    },
    {
      "path": "assets/ast_z.png",
      "kind": "asset",
      "id": "ast_z",
      "size": 2048,
      "sha256": "…"
    }
  ],
  "excludedArtifacts": [
    { "path": "documents/doc_x/index.md.bak", "reason": "recovery-artifact" }
  ],
  "warnings": []
}
```

规则：

- `files` 必须覆盖 DB 中每个 `documents`/`document_revisions`/`assets` 行；
  遇到“DB 有行但文件缺失” → **备份失败**，不允许静默跳过。
- “文件存在但 DB 无行”（孤儿）按类型处理：
  - `documents/{id}/index.md` 无对应 DB 行 → **默认失败**（可能是未提交创建或被误删的文档，
    必须先由 V1.1 恢复或管理员确认）；
  - `revisions/`、`assets/` 无对应 DB 行 → 默认记录 `warnings` 并**不打包**（它们不是已提交数据，
    重试清理即可）；设置 `INKFLOW_BACKUP_STRICT_ORPHANS=1` 时改为失败。
- 必须校验“Markdown 中引用、但 `assets` 表无行”的附件 ID：
  这类文件不会被 `document_assets` 覆盖，恢复后会变成坏图；发现即备份失败并列出文档/附件 ID，
  提示先运行附件对账或清理。
- `document_hash` 非空的文档，必须与 manifest 中的全文件 SHA-256 一致；`NULL` 的旧行记录 `legacy: true`。
- `assets.checksum` 为空的旧行（`listAssets` 对账产生的）用 manifest 实际哈希；
  恢复时回填 `assets.checksum`。
- `mtime` 只作参考，不作为完整性依据。

### 7.3 版本兼容

| 场景 | 行为 |
| --- | --- |
| `formatVersion` 不等于 1 | 拒绝（未来版本需显式支持） |
| `schemaVersion` < 当前 | 解压后按迁移链升级（`migrations.ts`） |
| `schemaVersion` > 当前 | 拒绝，提示升级 InkFlow |
| `appVersion` 不同但 `schemaVersion` 相同 | 允许，报告中记录警告 |
| 缺少 `manifest.json` | 拒绝 |
| 条目数量/大小超限 | 拒绝（防 zip bomb） |

### 7.4 安全

- 备份包含 `users.password_hash`、`recovery_codes.code_hash`、`shares`（哈希），
  **不含明文密码/初始化密钥/环境变量/API Key**。备份文件本身必须视为敏感文件：
  - POSIX 下目录 `0700`、文件 `0600`；
  - 恢复上传接口要求 owner 重新输入密码 + 明确确认字符串；
  - 文档说明备份应加密后离线保存（V1.2 不内置加密，可后续增加）。
- 解压/打包全程拒绝 symlink，且每个条目 `path.resolve` 后必须仍在 staging 根内。
- 条目文件名/ID 必须满足 `assertSafeId()` 的字符集；拒绝 `..`、绝对路径、驱动器号、NUL。

## 8. 备份一致性方案（逐步）

### 8.1 一次备份的时间线

```
t0  请求进入
t1  acquireExclusive()                     ← 阻塞所有文档/附件/历史写；读请求不阻塞
t2  recoverPendingDeletions/Saves()        ← 修复 V1.1 中断状态
t3  assertFileStateMatchesDb()             ← DB 行 ↔ 文件、hash、附件 checksum
t4  sqlite.backup() → staging DB           ← WAL 一致的 DB 快照
t5  scrub sessions + checkpoint + close
t6  hardlink/copy documents/revisions/assets → staging（带 manifest 骨架）
t7  release()                              ← 业务写入恢复；快照已冻结
t8  逐文件 SHA-256（读 staging）
t9  交叉校验 manifest ↔ staging DB
t10 zip: staging → backups/<id>.zip.part
t11 fsync + rename → <id>.zip + 整包 SHA-256
t12 写 backup_jobs、保留策略、清理 staging
```

- t1–t7 是唯一阻塞窗口，通常等于“遍历目录 + 建硬链接 + DB 备份”。
- t8–t12 不阻塞业务；即使业务继续写，硬链接快照也不变。
- 若 t2/t3 发现无法修复的问题 → 立即释放租约并失败，不生成“看起来成功”的包。

### 8.2 与 V1.1 机制的兼容

- **不关闭任何检查**：备份不会跳过 `prepareDocumentSave` 的 `.bak` 防护、
  `document_hash` 校验、路径包含校验、附件权限校验。
- 备份只读；唯一写操作是 `backups/` 下的 staging/ZIP/job 记录。
- `recoverPendingSave`/`recoverPendingDeletion` 仍按原逻辑运行；备份失败时列出需要管理员处理的文档 ID。
- 保存/删除的 HTTP 语义不变；备份期间它们只是**等待租约**，不会返回错误。

### 8.3 崩溃场景

| 崩溃点 | 结果 | 下次启动 |
| --- | --- | --- |
| t4 前 | 无 staging 或空 staging | 清理 `.staging`，删除锁 |
| t4 中 | staging DB 不完整 | 清理 `.staging`，任务标记 aborted |
| t6 中 | staging 文件不完整 | 清理 `.staging` |
| t10 中 | `.zip.part` 残留 | 删除 `.part`，不视为备份 |
| t11 后 t12 前 | ZIP 完整但无 DB 记录 | 按文件名/manifest 重建记录（可选） |
| 任意时刻 | 业务数据本身由 V1.1 机制保护 | 不受影响 |

### 8.4 磁盘空间与失败处理

- 打包前估算并检查剩余空间；不足 → `BACKUP_DISK_FULL`，保留 staging 供诊断或按配置清理。
- 任一文件读取失败（EACCES/EIO）→ 备份失败，不跳过。
- 任一 hash 与 DB `document_hash` 不匹配 → 备份失败，报告哪个文档；这通常意味着现场已不一致，
  应先运行 `/system/integrity` 或 V1.1 恢复。
- ZIP 生成失败 → 删除 `.part`，`backup_jobs` 记录错误，调度器下次重试。

## 9. 恢复流程及失败回滚方案

### 9.1 恢复入口

- Web：`POST /api/v1/restores`（owner + 密码二次校验 + 确认字符串），支持：
  - 上传 ZIP（原始流写入临时文件，限制大小）；
  - 指定已有备份 ID。
- CLI（灾难场景，服务无法正常启动时）：
  ```bash
  npm run restore -- --package /path/to/inkflow-....zip --data-dir /new/storage
  ```
  CLI 不启动 HTTP，只调用同一套 `RestoreService`。

### 9.2 恢复前检查

1. 包是否存在、大小是否超限、ZIP 是否可读；
2. `manifest.json` 是否存在且版本兼容；
3. 当前是否有未完成的保存/删除恢复；若有，先尝试恢复，失败则中止并要求先处理；
4. 当前环境是否已有数据；有数据则必须成功生成 `pre-restore` 备份，否则中止；
5. 剩余磁盘空间 ≥ 包解压大小 × 1.5 + 当前数据大小 × 1.2；
6. 当前进程是否持有 DB；恢复期间关闭。

### 9.3 恢复前数据保护

- 先创建 `kind=pre-restore` 的完整备份，放在 `backups/`，并在统计/保留策略中标记受保护。
- 再把当前 `documents/revisions/assets` 目录和 DB 文件移动到
  `backups/rollback-<restoreId>/`，**不直接删除**。
- `pre-restore` 备份失败 → 整个恢复中止（除非目标目录为空且显式 `--allow-empty`）。

### 9.4 恢复步骤（详细）

1. 进入维护状态（写 `.maintenance.json` + `.restore-state.json`）。
2. `acquireExclusive()`，等待所有在途写完成。
3. 解压到 `<dataDir>/.restore/<id>/`。
4. 在 staging 上做全量校验（见 5.7）。
5. 在 staging DB 上：
   - `DELETE FROM sessions;`
   - 规范化路径列：
     ```sql
     UPDATE documents SET file_path = 'documents/' || id || '/index.md';
     UPDATE document_revisions SET snapshot_path =
       'revisions/' || document_id || '/' || id || '.md';
     UPDATE assets SET storage_path = ? WHERE id = ?;  -- 来自 manifest
     ```
   - 对 `assets.checksum` 为空的行用 manifest 哈希回填；
   - `VACUUM`（可选）或 `PRAGMA wal_checkpoint(TRUNCATE)`。
6. `closeDatabase()`。
7. 移动当前目录/DB 到 rollback 目录。
8. 把 staging 的 `documents/revisions/assets` rename 到正式位置；DB 用“临时文件 + rename”到 `getDbPath()`。
9. `getDatabase()` → 执行 schema 迁移（`document_hash`、`user_version`、`backup_jobs` 等）。
10. 重建 FTS：清空 `documents_fts`，从每篇 `index.md` 解析正文后插入。
11. `backfillDocumentHashes()` 补齐 `NULL`。
12. `verifyLiveState()`：DB integrity、行数、documents/revisions/assets 交叉校验。
13. 写恢复报告 `backups/restore-reports/<id>.json`，清除维护状态，释放租约。

### 9.5 失败回滚

| 失败点 | 回滚动作 |
| --- | --- |
| 解压/校验失败（未动现场） | 删除 staging，清除维护状态，现场不变 |
| pre-restore 备份失败 | 中止，现场不变 |
| 关闭 DB 失败 | 中止，现场不变 |
| 换入部分成功 | 关闭 DB → 删除已换入的新目录 → 从 rollback 目录换回 → 重新打开 DB → 校验 |
| 换入后校验失败（schema/迁移/FTS） | 同上，并保留失败的新数据到 `backups/failed-restore-<id>/` 供诊断 |
| 回滚本身失败 | **不删除任何东西**；保留维护状态与状态文件，返回明确的手工恢复步骤（rollback 目录路径、DB 备份路径） |

回滚后必须再次 `verifyLiveState()`，并在报告中明确写出“已回滚到恢复前状态”。

### 9.6 恢复结果报告

```ts
interface RestoreReport {
  restoreId: string;
  ok: boolean;
  rolledBack: boolean;
  package: { fileName; sha256; formatVersion; schemaVersion; createdAt };
  sourceCounts: {...};
  restoredCounts: {...};
  durationMs: number;
  preRestoreBackupPath?: string;
  rollbackDir?: string;
  checks: VerificationReport['checks'];
  warnings: string[];
  error?: string;
}
```

5. **恢复必须二次输入 owner 密码 + 确认字符串**；CLI 需要 `--force` 才能跳过交互确认（仍会生成 pre-restore 备份）。
6. **恢复只换入 `documents/revisions/assets` 与 DB**，不整体 rename `storage/`。
7. **V1.2 不内置备份加密**；文档建议用户将 ZIP 加密后离线保存。后续可加 `INKFLOW_BACKUP_PASSPHRASE`。

### 已知限制

- 租约是**进程内**的；两个独立 Node 进程写同一 storage 仍不受保护（现有 `cluster.isWorker` 检查只挡住 cluster worker）。
- `listAssets()` 仍保留 GET 时对账的既有行为，但已加租约与互斥；更大规模时应改为显式维护操作。
- 删除文档后的资产清理仍同步执行，可能让删除请求耗时增加；后续可改为后台任务。
- 历史目录中由旧版本崩溃留下的“孤儿 revision 文件”不会在 Batch 1 自动删除（只保证不再产生悬空 DB 行）；备份前会将其作为 warning/失败项处理。
- 浏览器 `localStorage` 的评论/论坛数据仍不在服务端。
